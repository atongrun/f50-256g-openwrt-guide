# 备份有什么用，又恢复不了什么

本案例原始备份约 5.86GiB，覆盖 userdata 以外的 74 个命名分区、hardware boot0/boot1、主备 GPT 和选取的 Wi-Fi 配置。设备专属 NV、IMEI、校准留的是本机数据。备份没有上传到这个仓库。

没有备份整块 256GB 的原因，是用户明确同意清空 Android 应用和个人文件，并不需要 userdata 全量镜像。这个选择不能替其他用户做。

## 校验清单

- 每个分区的字节数等于实际预期大小。
- 设备源读取前后与电脑保存文件 SHA256 一致。
- GPT 头和分区数组 CRC 正确，主备互指、数组一致，分区都在可用范围内，没有重叠。
- 私密 manifest 记录读取时间、来源设备、工具版本、校验结果。
- 原始备份只读保留；后续阶段用新目录，不能用 B09 数据覆盖 B06 备份。

## 无法承诺的恢复

userdata 未备份，意味着应用、账户和个人文件无法靠这些分区镜像找回。metadata 的加密信息也不能替代 userdata。

RPMB、eFuse、硬件秘密没有被普通分区备份覆盖。在线 Android 读取虽逐个文件哈希稳定，也不是全机同一时刻的离线快照。

完整 BROM/下载模式恢复在本案例中没有实际演练。不能保证严重故障不拆机就能恢复。恢复时仍要核对加载器与固件链；不能把新旧启动链文件随意混搭。

本例后续缩过 userdata，所以原 GPT 是**历史布局证据**，不是随时可以写回的“恢复按钮”。恢复布局必须同时处理当前 Android/Linux 文件系统占用，不能只恢复 GPT。

## 优先恢复可用性

仅 Linux 网络故障但 SSH 可用时，优先用作者切换工具回到已验证的 Android。代理故障先停代理并恢复 DNS；别把它当作蜂窝固件损坏。

设备无法启动时，先判断 USB 枚举和当前启动模式，收集日志。不要连续刷 TrustOS 或用网上别人的“全备份”覆盖本机。只要涉及新的分区写入，就重新给出计划、备份和确认。
